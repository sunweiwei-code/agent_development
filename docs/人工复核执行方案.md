# 人工复核执行方案

> 适用版本：PRD V3.2　｜　复核对象：`path_type` 45 条、评测集 13 Q + 13 T
> 依据：PRD 5.4（标注完成后隔日复核）、5.5（评测集须冻结）

---

## 0. 一句话原则

**复核的对象是"判断"，不是"分数"。**

凡是只看分数就点头的复核，等于把 `score.py` 的结论抄一遍——上一轮已经证过这会出问题（探测排名第 1 的 L25、L36 都被人工排除了）。所以本次复核**先读原文、后看分数**，且判"不通过"必须给出引文依据。

## 1. 角色、时间盒与产出

| 项 | 内容 |
|----|------|
| 复核人 | 1 人（建议与初标不是同一人；若只能同一人，必须隔日做，且先盲判再看初标） |
| 时间盒 | path_type 45 条 ≈ 50 分钟（约 1 分钟/条）；评测集 Q 13 条 ≈ 30 分钟；T 13 条 ≈ 15 分钟；合计 **约 1.5 小时** |
| 工具 | `data/review/path_type_review.csv`、`evalset_q_review.csv`、`evalset_t_review.csv`（Excel 直接打开，UTF-8-BOM） |
| 回填校验 | 填完运行 `python scripts/apply_review.py`；确认无误后 `--apply` 落盘 |
| 产出 | 三张已填表 + `path_type.json` 改判结果（如有）+ 复核结论一段话 |

**复核表已预填"当前判定 + 计数 + 研究方向原文"**，复核人只需填最后 3 列。

## 2. 文件映射：每个阶段改哪里、落到哪里

**这一节是本文档最重要的部分**——复核的每一条结论都必须知道"填在哪个文件、最终写进哪个字段、由谁写"。

### 2.1 总表

| 阶段 | ① 填在哪（人工） | ② 落到哪（程序） | ③ 谁执行 | ④ 校验命令 |
|------|------------------|------------------|----------|-----------|
| 一 · `path_type` | `data/review/path_type_review.csv`<br>列 I「复核判定」/ J「改判为」/ K「复核依据」/ L「复核人」/ M「复核日期」 | `data/labs/path_type.json`<br>`[lab_id].path_type = [改判为]`、`.source = "review"`、`.evidence = {"复核改判": 依据}`<br>↓ 再经 `inject_l2.py` 同步到 `data/labs/labs.json` 的 `path_type` 字段 | `apply_review.py --apply` | `check_evalset.py` |
| 二 · 评测集 Q | `data/review/evalset_q_review.csv`<br>列 H「复核判定」/ I「逐条合理性确认意见」/ J「复核人」/ K「复核日期」 | `data/eval/queries.json`<br>`reasonable_set[]`（`lab_id`/`verdict`/`reason`）、`excluded[]`、`notes` | **人工改 JSON**（脚本只导出清单，见 2.3） | `check_evalset.py` |
| 三 · 评测集 T | `data/review/evalset_t_review.csv`<br>列 F「复核判定」/ G「op 是否属允许集」/ H「复核意见」/ I / J | `data/eval/instructions.json`<br>`expected[]`（`field`/`op`/`new_value`）、`notes` | **人工改 JSON** | `check_evalset.py` |
| 四 · 算子抽查 | `data/review/review_log.md`（新建，见 2.4） | `scripts/score.py`（同义词表 / 阈值 / 算子）<br>→ 若属规则缺口，另在 PRD 5.4 补 P 编号补丁 | **人工改脚本** | `python scripts/score.py` 手算对比 |

### 2.2 为什么阶段一能自动、二三不能

- 阶段一的改判是**封闭取值**（6 个 `path_type` 枚举之一），可以安全自动写回。
- 阶段二三的改判是**自然语言建议**（"建议把 L21 从合理选择集删除"），无法安全自动解析成结构化改动。脚本只把它们导出成待改清单，由人工落到 JSON。
  → 这是有意的：**宁可多一步人工，也不让脚本猜语义**。

### 2.3 阶段二的待改清单在哪

运行 `apply_review.py`（不带 `--apply` 也会生成）后，产物在：

```
data/review/todo_evalset.md
```

格式为三列：条目 / 目标文件 / 修改建议，B（改判）与 C（存疑）分开列。人工按清单改完 `queries.json` / `instructions.json`，再跑 `check_evalset.py`。

### 2.4 阶段四的记录文件

新建 `data/review/review_log.md`，每条抽查记四行：

```markdown
## 抽查 1 · L06
- 自拟 interest：视觉算法
- 人工判断：1.0（"计算机视觉"含"视觉算法"四字，应走子串命中）
- 机算结果：0.8（走同义词路径）
- 结论：判据偏差 —— 同义词组"视觉"命中先于子串判断，需在 score.py 中把子串判断提到最前
```

## 3. 三条独立原则

1. **盲评优先**：先自己判断，再对初标。表里"当前判定"列建议先遮住（Excel 选中该列 → 隐藏）。
2. **只认原文**：任何判定都要能指向 `research_areas` / `intro` / `achievements` 里的具体文字，不接受"感觉像"。
3. **判码制**：每条只允许三种结论，不允许"再看看"这种中间态：

| 码 | 含义 | 必填 |
|----|------|------|
| **A** | 维持 | 无需额外填（评测集 Q 侧例外，见 §4） |
| **B** | 改判 | 必填「改判为」+「依据 ≥15 字」 |
| **C** | 存疑 | 必填「依据 ≥15 字」，挂起待第三人裁决，不得直接冻结 |

## 4. 阶段一：`path_type` 复核（45 条）

> **填**：`data/review/path_type_review.csv`（列 I~M）　**落**：`data/labs/path_type.json` → 经 `inject_l2.py` 同步 `data/labs/labs.json`　**执行**：`apply_review.py --apply`

### 4.1 判断顺序（与 PRD 5.4 一致，不要跳步）

```
1. 先看"竞赛项 / 科研项"两个数和比值
2. 两类都 >0 且比值在 1:2~2:1          → 双主导
3. 两类都 >0 但不并重                  → 项数多的一方主导
4. 只有一类                            → 该方主导
5. 两类都是 0，但名称/intro 表明科研定位 → 科研主导（low）
6. 其余                                → 待确认（low）
```

### 4.2 复核时重点盯的四类记录

| 类别 | 为什么要盯 | 判断要点 |
|------|-----------|----------|
| `confidence = low` | L33 中德物联网（无 achievements） | 是否真的"无量化产出"，还是抽取漏了 |
| 计数贴近边界（比值 ≈0.5 或 ≈2.0） | L06 是 5:6=0.83、L05 是 28:38=0.74 | 任一边多数 1 项就会翻转，需确认计数依据 |
| 名称与内容冲突 | L07「教学实验室—算法俱乐部」判竞赛 | 以**内容**为准，不看名字 |
| 校企共建类 | L14 云创中心、L38 云智慧、L45 三维感知 | 校企≠就业；看 achievements 有无实习就业实据 |

### 4.3 标注示例

**示例 1 · 维持（A）**

```
lab_id: L06
实验室: 深技大-浙江大华《计算机视觉与人工智能》联合实验室
竞赛项 5 / 科研项 6 / 比值 0.83
当前判定: 双主导 (high)
复核判定: A
（A 无需填依据）
```

**示例 2 · 改判（B）—— 这是真实可用的场景**

```
lab_id: L38
实验室: 物联网软件与云计算应用实验室（物联网智慧云实验室）
竞赛项 7 / 科研项 1 / 比值 7.0
当前判定: 竞赛主导
复核判定: B
改判为: 教学平台
复核依据: "intro 明确『以建设云计算、物联网、大数据等工程领域的科学研究、
人才培养和学术交流平台为目标…为大学生提供实习实训服务』；7 项竞赛奖项是
附带产出，该室定位是教学实训平台，按 5.4 第二段 2.4 应判教学平台。"
```

> 注意写法：**引用原文 + 指出与规则哪一条对应**。只写"我觉得像教学平台"不合格。

**示例 3 · 存疑（C）**

```
lab_id: L21
实验室: 腾讯安全英才班实验室
当前判定: 就业项目主导 (medium)
复核判定: C
复核依据: "intro 同时具备两种定位——『特色课程…产学研合作』偏教学平台，
『优先提供实习就业机会』偏就业项目主导；5.4 的 2.3/2.4 谁优先未写明，
需第三人裁决后再定。"
```

## 5. 阶段二：评测集 Q 复核（13 条）

> **填**：`data/review/evalset_q_review.csv`（列 H~K）　**落**：`data/eval/queries.json` 的 `reasonable_set[]` / `excluded[]`（**人工改**）　**清单**：`data/review/todo_evalset.md`

### 5.1 三条必查

| 检查 | 判据 |
|------|------|
| **合理选择集逐条站得住** | 每条 `lab_id` 的理由都要能在 `research_areas` 里找到对应词。找不到 → B（建议删除该条）|
| **排除项不得是"漏标"** | 表里已列出被排除的探测结果。若你认为某条其实合理 → B（建议恢复）|
| **覆盖约束仍成立** | 改判会动覆盖。改完必须重跑 `check_evalset.py`，确认 12 个实验室、四种 path_type 仍满足 |

### 5.2 特别注意：不要被"排名"说服

已排除的三条里有**两条原本排第 1**（Q-12 的 L25、Q-13 的 L36）。若复核时看到"它排第一啊"就想恢复，说明又在按分数判断。判断依据只能是方向是否对口。

### 5.3 标注示例

**示例 1 · 维持（A，但必须写确认意见）**

```
id: Q-01
合理选择集: L06 / L29 / L01
复核判定: A
逐条合理性确认意见: "L06『计算机视觉』、L29『机器视觉』、L01『视觉识别算法和雷达算法的开发』
均与『视觉算法』直接对应；L01 另有 RoboMaster 建制，与『想打 RoboMaster』吻合。三条均成立。"
```

> Q 侧判 A **也要写意见**——这是脚本强制的，用来区分"读过"和"空过"。

**示例 2 · 改判（B）**

```
id: Q-03
当前: L39 合理 / L15 合理 / L21 允许不强求
复核判定: B
逐条合理性确认意见: "L21 分数 0.35 恰等于 MIN_SCORE，且定位是校企英才班（就业取向），
与『偏科研』不符。建议从合理选择集删除，避免 G-01 靠临界分撑住。
删除后本集合剩 L39/L15，仍非空。"
```

**示例 3 · 存疑（C）**

```
id: Q-08
复核判定: C
意见: "L14 亚马逊云创中心方向是『生物技术与人工智能的结合』，对『对 AI 感兴趣』
算沾边但对零基础是否合适，判断依赖主观；挂起待议。"
```

## 6. 阶段三：评测集 T 复核（13 条）

> **填**：`data/review/evalset_t_review.csv`（列 F~J）　**落**：`data/eval/instructions.json` 的 `expected[]`（**人工改**）　**校验**：`check_evalset.py`

### 6.1 四条必查

| 检查 | 判据 |
|------|------|
| 字段在白名单 | 7 个字段之一（`location` / `intro` / `achievements` / `research_areas` / `group_tags` / `recruit_info` / `contact`）|
| op 属该字段允许集 | 对象字段只能 `merge`；`location` 只能 `replace`；其余数组/字符串三个 op 均可 |
| `remove` 目标真的存在 | 否则实跑必然 `value_not_found` |
| `merge` 子键合法 | `recruit_info`⊂{window, accepts_freshman, note}；`contact`⊂{qq_group, email, wechat} |

> 以上四条脚本已自动校验（`check_evalset.py`），复核时重点是**语义是否合理**：这句话教师真的会这么说吗？op 选对了吗？

### 6.2 标注示例

**示例 1 · 维持（A）**

```
id: T-06
绑定: L02　原话: "去年那条省级奖项写错了，删掉"
期望: achievements / remove / "省级奖项合计498项"
复核判定: A
复核意见: "已核对该条确实存在于 L02 的 achievements（第 4 条），op=remove 属允许集，
删除目标可整段匹配。"
```

**示例 2 · 改判（B）—— 真实案例**

```
id: T-09
绑定: L01　原话: "把组别改成机械组、电控组、视觉组"
期望: group_tags / replace / ["机械组","电控组","视觉组"]
复核判定: B
复核意见: "原数据 group_tags 曾被解析成 ['分成四个组','别分别是机械组','电控组',…]
这种碎片（分词把句子切碎了），已修复为 ['机械组','电控组','视觉组','运营组']。
本条期望值缺『运营组』，但教师原话确实只说了三个组，属『教师主动删掉一个组』的
合法场景，建议保留 remove 掉的语义，改期望值为 ['机械组','电控组','视觉组'] 并
在 notes 注明『教师未提运营组，等同删除』。"
```

## 7. 阶段四（建议加做）：打分算子抽查

> **填**：`data/review/score_spotcheck.csv`（脚本生成）　**落**：`scripts/score.py`（同义词表/算子/阈值）　**校验**：命中真伪逐条判

**做法（不是对答案，是看命中真伪）**

```bash
python scripts/spotcheck_scoring.py                 # 默认 5 个词
python scripts/spotcheck_scoring.py --terms 视觉算法 边缘计算
```

脚本走的是 `score.py` 里**真实的** `op_match_detail`（带归因），不是复制一份逻辑——否则抽检的是副本。

每个词展开为"在 45 条实验室上的全部命中项 + 命中方式（子串/同义词/n-gram）"，人工只需判"这条命中是真是假"。

**如何一眼看出问题**

| 信号 | 含义 | 表里的位置 |
|------|------|-----------|
| 命中率 ≥25% | 同义词组过宽（一个词命中一大片） | 控制台「预警」列 |
| 零命中 | 可能是真无此方向，也可能词组漏词 | 同上 |
| 「字面沾边 = 否」 | 纯同义/近义命中，**最容易错** | CSV 该列，优先看这几行 |

**判定后如何处理**

判「错」的行 → 改 `score.py` 的同义词组或算子 → **必须重跑 `calibrate_min_score.py`**（改算子会动分数分布，`MIN_SCORE=0.35` 的标定结论可能失效）。

`score.py` 是所有判断的底座，它错了整条链都错。建议抽 5 条随机实验室做一次"手算 vs 机算"：

```
1. 随机取 5 条 lab，打印 research_areas
2. 用一个自拟的 interest，人工判断应得几分（1.0 / 0.8 / 0.6 / 0）
3. 跑 score.py 对比
4. 不一致 → 记录到复核表备注，进"规则补丁"清单（像 P1~P7 那样写进脚本注释）
```

重点验证同义词表：`_syn_hit` 目前是"词组双向包含"，容易过宽（"数据分析"组曾让 12 条实验室同分 0.63）。

## 8. 回填与落盘

```bash
# 1) 填完三张表后，先只校验
python scripts/apply_review.py

# 2) 确认无错、且无 C 挂起项，再落盘（会自动备份 + 重跑评测集自检）
python scripts/apply_review.py --apply
```

校验规则（脚本强制）：

- 未填判定 → 报错
- 判 B 没给「改判为」或依据 <15 字 → 报错
- 判 C 没写待议点 → 挂起
- **Q 侧判 A 但没写确认意见 → 报错**（防空过）
- `--apply` 后自动跑 `check_evalset.py`，覆盖约束被破坏会立即暴露

---

## 9. 冻结条件

复核通过（可冻结）需同时满足：

- [ ] 三张表全部填写，`apply_review.py` 无报错
- [ ] **C 类挂起项 = 0**（有挂起则不冻结，先裁决）
- [ ] `check_evalset.py` 全部通过（G-01 覆盖 ≥6 实验室、四种 path_type、含双主导、产生推荐触达 ≥10）
- [ ] 若 `path_type` 有改判，**评测集已重跑**且合理选择集未被破坏
- [ ] 复核人在表末签字 + 日期

冻结后在 PRD 标注「V3.3 复核通过，YYYY-MM-DD」，此后改评测集须重走本流程。

## 附：本次复核已提前发现的问题（示例价值）

在准备复核表时，用脚本核对 `group_tags` 发现：

| 问题 | 现象 | 处理 |
|------|------|------|
| L01 组别被切碎 | `["分成四个组", "别分别是机械组", "电控组", "视觉组", "运营组"]` | 已修 `parse_group_tags`（先切到"分别是"之后再提取 `X组`），现为 `["机械组","电控组","视觉组","运营组"]` |

这类"表里看不出来、一跑就露"的问题，正是复核阶段要抓的——**复核不只是看结论对不对，也是看数据形态对不对**。
